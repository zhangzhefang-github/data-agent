# 问数回合收尾

## 2026-11-23 的决定

2026-11-23，用户要求优化订单主题空间的问数回合，优先级为：

1. 统一一份问数终态，聊天流、会话历史和评测读取同一份，不各自推导。这与 [ADR 0008](../adr/0008-order-query-clarification.md) 一致。
2. 在问数回合内部收紧澄清。不新增独立澄清代理，也不做开放式意图路由。
3. 上一轮已验证的结果行进入下一轮提示。去年同期仍按 [ADR 0003](../adr/0003-direct-sql-duckdb-first.md) 重放最近一次成功 SQL，不改成第二条执行路径。

同日确认的澄清规则：只有缺失信息会改变业务结果、且没有安全默认值时才追问。展示方式、排序和已经写明的执行顺序不追问。指标口径冲突、时间范围不明、业务对象歧义仍要澄清。不为了少追问而猜测口径。

同日点名的回归题是：2018-01-01 至 2018-04-09 订单金额最高的 10 位客户，再按客户和订单状态给出订单笔数和订单金额。预期不澄清，一条只读查询里完成排名和分组。[ADR 0007](../adr/0007-readonly-sql-with-fanout.md) 不允许把同一问题拆成两条串行 SELECT。

## 2026-11-23 盘点

盘点对象是工作树 `/home/zzf/data-agent-chat-integration`，分支 `implement/orders-chat-34`，提交 `4115fe0`，另有当日未提交改动。本仓库工作区 `main` 在 `53a930d`，没有这套聊天集成。下面的代码事实只在该提交加未提交改动上成立。

- 一轮会把 `outcome` 写入 `messages`，并放进 SSE 的 `done`。构造点仍散在 `chat()` 的各出口，没有单一构造函数。SSE 的 `done.status` 仍是 `completed` / `failed`，和 `outcome.status` 并列。
- 评测在观察里已有 `outcome` 时采用它的 `status`。观察里没有 `outcome` 时，评测仍自行推出 `invalid_output`、`success` 或 `model_error`。
- 前端在非 `success` 时，除范围说明外，用 `outcome.reason` 替换正文。
- `decide()` 对仅未发布平均、姓名、客户数、成功订单、金额相加、排名口径不明会在进模型前结束。点名回归题不过这条预检。
- 未提交改动里，该题若被模型写成「展示 A 还是 B」，工具把它当成 SQL 修复，不写成用户澄清。三次仍不执行则是 `validator_error`。测试 `test_specified_breakdown_rejects_a_presentation_choice` 锁的是这条修复，不是「模型第一次就交出分组 SQL」。`orders_golden.json` 没有这题的期望行。
- 下一轮提示只拼接校验过的上一轮 SQL。结果行存在 `messages.result`，不进入提示。

## 最小改动顺序

2026-11-23，约定每次只动一个边界，先补测试再改。不把散落的出口收成新的路由模块。

1. 终态：持久化的正文就是用户看见的字；`outcome.status` 是唯一状态。前端在正文非空时不再用 `reason` 替换。评测只在观察没有 `outcome` 时保留现有兜底。
2. 澄清：点名回归题直接提交一条分组 SQL 时不得出现澄清。展示选择继续当修复，不向用户追问。期望行从订单库算出后写入对照，不新写校验器。
3. 提示：在已有的上一轮 SQL 旁附上已验证结果行。去年同期的执行路径不动。
