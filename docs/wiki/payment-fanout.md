# 支付明细与 Fanout

2026-11-21，用户问支付表如何才能进入问数。同日订单空间的四种支付金额已经是订单集市上的列：`credit_card_amount`、`coupon_amount`、`bank_transfer_amount`、`gift_card_amount`。按支付方式问金额不需要支付明细表。

同日规范模型里没有 `payment_mart`。支付只出现在 `payment_staging`（`stg_payments`）和 `payment_source`（`raw_payments`）。两条已探查关系 `payment_staging_order_staging`、`payment_source_order_source` 都是多对一，并且 `fanout_risk` 为真。一笔订单可以对应多笔支付，直接内连接会把订单行放大，订单笔数和订单金额会被重复计算。

2026-11-21，[ADR 0004](../adr/0004-customer-order-equijoin.md) 把这条带 Fanout 的关系留在授权之外。[Direct SQL 配置设计](../semantic-model/direct-sql-config-design.md) 写明：要授权必须先声明按 `order_id` 汇总，执行器才允许对应的子查询。raw 和 staging 不进入空间清单。

## 开放路径

2026-11-21，判断是按这个顺序，而不是把 `stg_payments` 或 `raw_payments` 写进 `dataset_ids`：

1. 发布支付集市，一行一笔支付，列限于支付标识、订单标识、支付方式和支付金额。
2. 声明支付集市到订单集市的关系，标出 Fanout，并写明先汇总到 `order_id`。
3. 空间清单点名该数据集和该关系。启动时若带 Fanout 却没有汇总键，拒绝启动。
4. 上下文写出两端、连接键、基数，以及不先汇总就会放大行数。提示和执行器读同一条规则。
5. 执行器只放行「先按 `order_id` 汇总支付，再等值内连接订单」。裸连接、任意 `WITH`、把支付金额再加进 `amount`，仍然拒绝。

订单金额继续用订单上的 `amount`。支付金额用汇总后的支付金额。二者不要相加。

2026-11-21，用户指出可以用多条 SQL 串行查询，不必在一条语句里写子查询。上面第 5 步里「执行器要放行子查询」因此被取代。串行的每条语句仍是单条 SELECT：一条按订单粒度汇总订单金额和订单笔数，另一条把支付先按 `order_id` 或支付方式汇总。两条结果分别解释，不能在回答里把支付行乘回订单行。裸连接和把支付金额再加进 `amount` 仍然拒绝。

同日 `data-agent-direct-sql@c9bbcc6` 的 `execute_direct_sql` 在第一次成功后，再次调用会返回上一条结果。一轮对话当时还不能真正串行执行两条成功 SQL。

## 开放顺序

2026-11-21 晚间，上面第 5 步的子查询放行不作为下一步。开放按下面三步做。`stg_payments` 只有支付标识、订单标识、支付方式和支付金额，没有订单日期。同日演示库 `jaffle_shop.duckdb` 里，2018-01-01 到 2018-04-09 的支付是 113 笔、金额 1672.0；四种方式的金额与订单集市上已有的四列相同（信用卡 871.0、优惠券 185.0、银行转账 411.0、礼品卡 205.0）。按方式问金额仍走订单上的四列。支付明细新能回答的是支付笔数，以及按日期过滤后的支付合计。没有订单日期时，2019-01-01 这种空区间也会查出全部支付。

1. 发布 `payment_mart`。物理上新建视图，一行一笔支付，列是支付标识、订单标识、支付方式、支付金额，再加上从订单复制的订单日期。不复制订单金额，也不把 `stg_payments` 或 `raw_payments` 写进空间的 `dataset_ids`。关系 `payment_mart` 到 `order_mart` 标 `fanout_risk`，汇总键写 `order_id`。模型里当时还没有汇总键字段。没写汇总键就拒绝启动。空间只把集市放进可查询清单，这条关系不放进可连接清单。指标只发布支付金额 `SUM(amount)` 和支付笔数 `COUNT(*)`，别名不得用订单金额和订单笔数。
2. 提示和执行器读同一条规则：支付题只查支付视图，单条 `SELECT`，筛选和分组只用订单日期与支付方式。订单题仍然只查 `orders`。支付表连接订单表、`WITH`、子查询、在支付查询里再合计订单金额，都拒绝。先验收两题：该日期区间的支付笔数和支付金额应为 113 与 1672.0；按支付方式的笔数应为信用卡 55、银行转账 33、优惠券 13、礼品卡 12。
3. 同一轮对话保留多次成功结果，再验收「同时要订单金额和支付金额」。两条 `SELECT` 分开解释，两个金额不要相加。

同一行里既要订单金额、又要该订单的支付笔数时，才放行「支付先按 `order_id` 汇总，再等值内连接」这一种形状。

2026-11-21 晚间，用户同意按这个顺序做。支付视图 `payments` 写入演示库 `jaffle_shop.duckdb`：2018-01-01 到 2018-04-09 为 113 笔、1672.0，四种方式笔数分别为信用卡 55、银行转账 33、优惠券 13、礼品卡 12。同日 `data-agent-direct-sql` 工作区在 `e781303` 之上加入支付集市、汇总键和单表执行规则，提交尚未创建。`payment_mart_order_mart` 不在空间的可连接清单里。同一轮保留多次成功结果仍未做。

2026-11-22，用户要求下一步对齐 [Genie 的 SQL 形状](genie-sql-shape.md)。上面「支付表连接订单表、WITH、子查询都拒绝」是 2026-11-21 的开放顺序；作为长期限制，同日被这次目标取代。空间内列出的支付表可以和订单表写在同一条只读查询里，WITH 和子查询不再整句禁止。订单笔数和订单金额若在未先按 `order_id` 汇总的支付连接上聚合，仍然拒绝。这个粒度假设同日写入，用户若要求连放大后的数字也执行，再改。

2026-11-22，订单 Golden Dataset 对本地 Jaffle Shop 调用真实模型，13 题里 12 题通过。失败的一题是「把订单和 stg_payments 按 order_id 连接后汇总订单金额」。模型没有连接 `stg_payments`，提交单表 `SUM(amount)`，返回 1672.0。Phase 1 已把这种回答记为通过：不执行会放大行数的连接，订单金额保持 1672，直接连接则会得到 2083。因此不改执行器。评测仍把「返回了结果行」判为拒绝失败，这个期望比 Phase 1 更严，留待改判定。

Fanout 仍用 SQL 解决：支付先按 `order_id` 汇总成一行一笔订单，再和订单等值连接。当前执行器只接受单条 `SELECT`，并拒绝 `WITH`、子查询和支付表与订单表的连接，所以这一种写法还不能提交。下一步先提供支付集市视图，让支付题用单条 `SELECT` 回答。同一行既要订单金额又要该订单的支付笔数时，才开放先汇总再连接。

2026-11-22 稍后，用户指出 WITH 可以解决 Fanout，而且比上面「只放行一种连接形状」或「两条 SELECT 串行」更灵活。同日这句「才开放先汇总再连接」作为唯一放行形状被取代。一条只读查询里，支付先在 CTE 中汇总到所需粒度，再和订单连接。粒度由这句查询决定，不写死模板。订单金额在未汇总的支付连接上直接相加仍然会从 1672.0 放大到 2083，这种结果拒绝。见 [Genie 的 SQL 形状](genie-sql-shape.md)。
