# 一条只读查询用 WITH 处理 Fanout

2026-11-22 决定：订单主题空间的 Direct SQL 只保留两条执行限制，对齐 Databricks Genie 的问数限制。语句必须只读，而且只能访问该空间列出的表。一条 SELECT 可以包含 WITH、子查询、这些表之间的 JOIN、GROUP BY 和窗口函数。

Fanout 在这条查询里解决。多的一侧先在 WITH 或子查询中汇总到指标基础粒度，再与少的一侧连接。不规定唯一的 JOIN 模板，也不把同一问题拆成两条串行 SELECT。订单笔数和订单金额的基础粒度仍是一笔订单。支付明细未先汇总就连接订单后，再汇总订单金额，会把 1672 放大成 2083，这种结果拒绝。支付金额不并进订单金额。raw 和 staging 不进入默认空间清单。

这取代 [ADR 0005](0005-payment-mart-single-table.md) 里「拒绝 WITH、子查询和支付表连接订单表」，以及 [ADR 0003](0003-direct-sql-duckdb-first.md) 里「每条 JOIN 先逐条授权才允许出现在 SQL 中」。空间清单仍然决定能看见哪些表。[ADR 0004](0004-customer-order-equijoin.md) 的客户–订单等值内连接仍然有效。`data-agent@f9bc191` 的校验器还拒绝 WITH，本决定先于那次实现。

## 考虑过的做法

- 继续禁止 WITH、子查询和支付连接。模型写不出先汇总再连接的 SQL，Fanout 只能靠不让连接发生。
- 同一轮里发两条 SELECT，各自汇总后再由回答拼起来。能避开一行放大，但同一行既要订单金额又要支付笔数时要靠模型对齐两次结果。
- 只放行「支付按 order_id 汇总后再等值内连接」这一种形状。能保住 99 和 1672，换一种分组就要再改校验器。
- 空间内的表任意连接，放大后的订单金额也执行。和 Genie 的句法一样宽，但会把订单金额报成 2083。

选定 WITH，是因为它能按问题选择汇总粒度，同时仍能拒绝停错粒度的订单指标。
